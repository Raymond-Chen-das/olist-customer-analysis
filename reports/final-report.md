# Olist 客戶分析與高潛力客戶挖掘 — 成果報告

> 視覺化版：`index.html`（GitHub Pages 首頁）；細部圖：`outputs/*.html`。

## 1. 摘要（Executive Summary）

**問題定義。** 在巴西電商 Olist 的多表交易資料上，用關聯式資料庫 + SQL 建立客戶層級行為分析、RFM 客群分群，並從新客中挖掘「高複購潛力」的少數客戶——對應資料分析師職缺的兩條工作內容（客戶屬性/消費行為分析、潛在客戶挖掘）。

**主要發現（3 點）。**
1. **97% 客戶只買一次**（複購率 3.0%）：留存困難，獲取品質與首單體驗是主戰場。
2. **高價值客群佔 16.5% 客戶、貢獻 31% 營收**（典型 80/20），可據以分配行銷資源。
3. **複購由「首單品類」驅動**（家用/可補貨 vs 一次性嗜好，差距約 6×）；配送/評論等服務體驗影響的是**滿意度（Spearman rho=−0.24）、不是留存**（假設檢定 p=0.16 / 0.25 不顯著）。

**結論與建議。** 依 RFM 客群分配資源（VIP 維繫、流失召回、新客育成）；獲取與交叉銷售聚焦高複購品類。

**適用邊界（不可省略）。** 結論基於 Olist 交易型電商資料。複購預測模型上限約 ROC 0.6，是「僅憑首單交易資料」的天花板，而非方法或執行的問題。

## 2. 資料說明
- **來源/範圍**：Olist 公開資料集 9 張表；訂單購買時間 2016-09-04 → 2018-10-17。
- **資料契約**（`docs/data-contract.md`）：99,441 訂單、96,096 不重複客戶；外鍵關聯零孤兒；已知良性缺失（評論自由文字）。
- **已知限制/偏差**：`customer_id` 每單變動（已改用 `customer_unique_id`）；review_id 827 重複（以 order 聚合）；F 維度退化（97%=1）。
- **有效訂單定義**：僅 `order_status='delivered'`（96,478 筆），排除取消/未實現消費。

## 3. 分析方法（依據與取捨）
- **客戶主鍵**：`customer_unique_id`（避免複購率全錯）。
- **RFM 分群**：R + log(M) 為主（F 退化）；傳統 NTILE 評分箱（SQL）為行動依據，K-means(k=3, silhouette 0.36) 作結構驗證——兩法獨立還原同一 R×M 結構（Champions 99% 同群）。
- **複購挖掘**：視為排序問題（base rate 3%）。特徵僅用「首單當下 + 客戶屬性」以**杜絕洩漏**（聚合 RFM 會內含結果，明確排除）。LogReg(balanced) 為主、XGBoost+SHAP 對照。
- **排除的方法**：以 Accuracy 評估（不平衡下無意義）；以聚合 RFM 當預測特徵（洩漏）；以服務體驗為主特徵（EDA 證實無預測力）。

## 4. 結果
| 項目 | 結果 |
|---|---|
| RFM 客群 | 6 群，各 15–20%；高價值 16.5% 客戶 → 31% 營收 |
| 複購模型 PR-AUC | 0.050（baseline 0.030，1.69×）；XGBoost 0.061（2.06×） |
| 複購模型 ROC-AUC | 穩健 **0.592 ± 0.008**（5 種子）；seed-42 0.611 |
| Top-decile lift | **1.8×**（前 10% 捕獲 ~18% 複購者） |
| 驅動因子 | 品類為主：home_appliances OR 3.6 … electronics/luggage OR 0.5–0.6 |

## 5. 結論限制與建議
- **壓力測試**（`docs/evaluation-report.md`）：種子穩定（±0.008）；時間外推 ROC 0.574；移除品類退至 0.563（量化品類貢獻）。
- **適用條件**：結論成立於 delivered 訂單、180 天複購窗、首單 ≤ 2018-04-20 的建模集。
- **標籤 caveat**（獨立程式碼審查發現）：複購以 delivered 第二單偵測、cutoff 以購買日計，窗末尾未送達之複購計為負樣本（**保守偏誤、不膨脹指標**）。
- **後續建議**：要真正提升複購預測，需 Olist 沒有的行為/行銷/競品資料（如瀏覽行為、行銷接觸、競品價格）。

## 6. 可重現性
- Python 3.13.3；套件版本見 `requirements.lock.txt`。
- 隨機種子全固定（split / KMeans / 模型 = 42）。
- 由 raw CSV 確定性重建：依序執行 `00_validate_contract.py → 07_stress_test.py → 08_report.py`。
- 獨立程式碼審查結論：substantially leak-safe；報告指標未受污染。
